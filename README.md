# ModularBlazor.Module.ContentDesigner

ContentDesigner: a runtime module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform)
platform, in [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture) layers. It is the newsroom's
post designer. It opens a post of a known kind (news, article, ...) with the contents its sections work on, and arranges
them in four views: Mobile, Tablet, Desktop and AMP. It checks each view against the kind's schema, fills the JSON-LD
automatically, and saves block and document templates. See [docs/design-plan.md](docs/design-plan.md) for the agreed
plan and its phases.

> **Status: phase 5, studio v1.** The designer's model, checks, templates, rendering (HTML and AMP), API and the
> studio (`/contentdesigner/studio/{postId}`, which arranges a post in its four views) are in. See
> [docs/studio-v1-plan.md](docs/studio-v1-plan.md) for what v1 holds and what it leaves for later.

The module's id, route prefix and database schema are `contentdesigner`.

## The model

A **post design** belongs to one post (of Content) and has a draft and, once published, a published state. Both hold
four **views**: Mobile, Tablet, Desktop and AMP. A view is a tree of **regions** (section, row, column; at most four
deep) and **placements** of the post's parts in them: a root value of the post's kind (`prop:headline`), one content
(`content:{contentId}`), or `items` (every content not placed by name, in the post's order). Regions and placements
carry editorial **tokens** (width, align, spacing, tone, size, level, aspect, columns, layout) and a span, an order and
a hidden flag. A view may inherit another instead (Tablet, Desktop and AMP inherit Mobile in the starter). Mobile,
Tablet and Desktop share one tree, so a part cannot move to another region between them, only reorder, resize or hide.

A **document template** is a design for a kind, made from scratch or saved from a post (the post's own contents fall
into `items`); one per kind may be the default that new designs start from. A **block template** is how one block
field shows in a view (part order, hidden parts, tokens and, optionally, starting values); a placement of a content
can name one.

**Checks** (`POST .../design/check`, and before every publish): the parts exist; required values and contents show in
every view; contents' tokens are their fields' styles; block templates fit their contents; web views do not reparent;
visual order against reading order, and heading levels (warnings); the AMP view uses renderers with an AMP variant;
DynamicFields validates the post and builds its JSON-LD, which must have headline, image, datePublished and author;
and the AMP page passes the AMP rules. Errors block publishing; warnings do not. Publishing pins the content revisions
it was checked against.

## API

Under `/api/contentdesigner`. Every call except the render routes needs a signed-in caller in a tenant (`X-Tenant`
header or the token's tenant). Edits send the `version` they read and get 409 if the design changed meanwhile.

| Method and route | Permission | What it does |
| --- | --- | --- |
| `GET /designs?page=&pageSize=&kind=` | `read` | One page of designs, the latest change first |
| `GET /posts/{postId}/design` | `read` | The design: draft and published state |
| `POST /posts/{postId}/design` `{ templateId? }` | `arrange` | Make it from a template, else the kind's default, else the starter; 409 if it exists |
| `PUT /posts/{postId}/design` `{ version, views }` | `arrange` | Replace the draft's four views |
| `PUT /posts/{postId}/design/views/{view}` `{ version, design }` | `arrange` | Arrange one view (`mobile`, `tablet`, `desktop`, `amp`) |
| `POST /posts/{postId}/design/apply-template` `{ version, templateId, views? }` | `arrange` | Take a document template's views (all, or those named) |
| `GET /posts/{postId}/workspace?culture=` | `read` | What the studio opens: the post, its contents (stage, section, assignee, revisions, drift), the render document, the kind's values and field styles, the design |
| `GET /posts/{postId}/events?after=` | `read` | The post's change feed in Content, after an event id (the studio's hot reload) |
| `POST /posts/{postId}/design/check` `{ views?, culture?, design? }` | `read` | The checks: errors and warnings, per view, and the JSON-LD; of the unsaved views when `design` is sent |
| `POST /posts/{postId}/design/preview` `{ amp, culture?, views? }` | `read` | The draft, or unsaved views, as the page or the AMP page (with its AMP issues) |
| `POST /posts/{postId}/design/publish` `{ version, culture? }` | `publish` | Publish once the checks pass; 409 lists the errors |
| `POST /posts/{postId}/design/unpublish` `{ version }` | `publish` | Take the published design down |
| `DELETE /posts/{postId}/design?version=` | `arrange` | Delete the design |
| `GET /document-templates?kind=`, `GET /document-templates/{id}` | `read` | Document templates |
| `POST /document-templates`, `PUT` and `DELETE /document-templates/{id}` | `templates` | Create (optionally as the default), edit, delete |
| `PUT /document-templates/{id}/default` `{ isDefault }` | `templates` | Make it its kind's default (the other default stops being one) |
| `POST /posts/{postId}/design/save-as-template` `{ name, description?, makeDefault }` | `templates` | Save the draft as a document template |
| `GET /block-templates?field=&view=`, `GET /block-templates/{id}` | `read` | Block templates |
| `POST /block-templates`, `PUT` and `DELETE /block-templates/{id}` | `templates` | Create, edit, delete |
| `POST /posts/{postId}/design/views/{view}/save-block-as-template` `{ part, name, withContent }` | `templates` | Save how a content shows in a view as a block template |
| `GET /render/{publicId}?culture=` | anonymous | The published post as its responsive HTML page |
| `GET /render/{publicId}/amp?culture=` | anonymous | The published post as its AMP page |

The permissions are `contentdesigner.read`, `contentdesigner.arrange`, `contentdesigner.templates` and
`contentdesigner.publish`.

The designer reads posts from Content (`/api/content/posts/{id}`, and the public `/api/content/public/{publicId}` for
renders) and fields from DynamicFields (field versions, validation, JSON-LD) over HTTP through the gateway, with the
caller's token; never in process.

## Rendering

`ContentDesigner.Rendering` renders a design with .NET's `HtmlRenderer`, so the server pages, the preview and the
studio's canvas run the same Razor components. Each starter block field has a renderer (`block.heading`, `text`,
`paragraph`, `quote`, `image`, `video`, `audio`, `gallery`), with an AMP variant where the HTML differs (`amp-img`,
`amp-video` or `amp-iframe`, `amp-audio`, `amp-carousel`); any other field falls back to a generic renderer.

The responsive page merges Mobile, Tablet and Desktop into one tree. Tokens become `data-mb-{token}` attributes, with
`-md` (Tablet) and `-lg` (Desktop) variants where those views differ, plus `data-mb-order-*`, `data-mb-span-*` and
`data-mb-hidden-*`; regions carry `data-mb-region` (their kind) and `data-mb-region-id`. MudTail's editorial
stylesheet styles them. The AMP page is the AMP view alone, with the boilerplate, the runtime, the extension script of
each component it uses and a generated base-only stylesheet in `<style amp-custom>` (under 75,000 bytes).

The render routes cache each page in memory per tenant, post, publish time, design version, culture and AMP or web,
for `ContentDesigner:RenderCacheMinutes`; a new publish of the post or of its design is a new key.

**AMP checks.** `AmpChecker` checks the rules of the official validator that this renderer could break: doctype,
`<html amp>`, charset first, viewport, canonical, boilerplate, runtime, allowed scripts and their extensions, no
forbidden tags, CSS only in `amp-custom` (no `!important`, under the size limit), no `style` attributes or event
handlers, sized layouts, https media. They run on every preview, check and publish, and in the unit tests. The
official validator (the `amphtml-validator` npm package) runs too when asked; it needs Node and the network:

```powershell
$env:CONTENTDESIGNER_AMP_VALIDATOR = '1'; dotnet test tests/WebApi.Modules.ContentDesigner.UnitTests --filter TheOfficialValidatorPassesTheAmpPage
```

## Settings

Change them on the Host Modules page.

| Setting (`ContentDesigner:`) | Default | What it is |
| --- | --- | --- |
| `MaxPageSize` | `100` | The largest page of designs |
| `ApiBaseUrl` | `http://localhost:5080` | The gateway, for the calls to Content and DynamicFields |
| `SiteBaseUrl` | (empty) | The public site, prefixed to a post's permalink for the canonical link |
| `AmpUrlTemplate` | `/api/contentdesigner/render/{publicId}/amp` | The AMP page's address, for `rel=amphtml` |
| `AssetUrlTemplate` | `/api/storage/items/{id}/content` | An asset's address |
| `Stylesheets` | MudTail's core and editorial CSS | The responsive page's stylesheets, comma separated |
| `RenderCacheMinutes` | `10` | How long a public page stays cached (0: not cached) |
| `ServiceAuthority`, `ServiceClientId`, `ServiceClientSecret` | (empty) | An optional client-credentials client for anonymous renders; without it a public page renders without JSON-LD |

In the Blazor client, the **ContentDesigner** menu entry opens the Designs page (`/contentdesigner`): the designs a
page at a time and the document templates, optionally of one kind. A row, or a post id, opens the studio.

## The studio

`/contentdesigner/studio/{postId}` arranges one post (a post without a design gets one: the kind's default template,
else the starter). It is a MudDock workspace whose panes are dock panels, declared with the platform's dock-panel
contract (`[assembly: DockPanel(..., ForStudio = "contentdesigner", ForContext = ["content.post"])]`) and mounted
through the host's `mb-module-panel` root component; other modules add their own panes to it the same way. The page
sets the page context `content.post` to the post id; every pane finds the open session by it.

| Pane | Where | What it does |
| --- | --- | --- |
| Designer | centre | MudCanvas over the Rendering components: the post as published, live, in the current view's device frame. Click selects; Alt+↑/↓ reorders; Delete takes a part out; the handle sets the span; Ctrl+Z / Ctrl+Y |
| Output | centre | The server's responsive or AMP HTML of the unsaved views, with the AMP issues and CSS size |
| Contents | left | The contents tray: each content's stage, section, assignee, review note, drift and where it shows; the post's values |
| Structure | left | The region tree of the current view: add sections, rows and columns; place what is not placed |
| Properties | right | The view's inheritance (give it its own design, or inherit another); for the selection: region, order, span, hidden, tokens, copy to another view, take it out |
| Templates | right | The kind's document templates: apply (all views or the current one), make default, save this design as one |
| JSON-LD | right | The post's JSON-LD, from the last check |
| Problems | bottom | The checks of the unsaved views; a problem selects what it names |
| Activity | bottom | The post's change feed; the studio polls it every 4 seconds while visible and reloads what the sections change |

Views only reorder, hide and restyle one content tree: Mobile, Tablet and Desktop share their regions, so a structural
edit in one applies to every web view with a design of its own; AMP has its own tree. A view that inherits another is
given its own copy on its first edit. Edits stay in the browser (undo 50 deep) until Save; Publish saves first.
Styling is editorial tokens only.

## Building

```bash
dotnet build
```

```bash
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform). Add a migration for every
database provider after a model change:

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.ContentDesigner.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.ContentDesigner.Infrastructure.Data.Migrations
```

After an endpoint change, export the module's OpenAPI document again (the entry project is `Web`). The next build of
`WebApi.Modules.ContentDesigner.Client` regenerates the typed client from it (NSwag); commit both, so client changes show
up in review:

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.ContentDesigner.Web -ModuleId contentdesigner `
    -Output <this repo>/src/openapi/contentdesigner.json
```

## Installing

The server part is the build output of `WebApi.Modules.ContentDesigner.Web` (`bin/<Configuration>/net10.0`: every layer, the Rendering library
plus the private Mediator and Ardalis.Result). Zip it and upload it on the client's Host Modules page
(`/host-modules`, as a platform admin), then activate it: the tenant migrations run per tenant, the routes are mapped
under `/api/contentdesigner`.

The client parts are uploaded on the client's Client Modules page (`/client-modules`), the API client first:
`soft.square.net.WebApi.Modules.ContentDesigner.Client.dll` (hidden; other client modules may depend on it), then the UI
as a .zip of `soft.square.net.Module.ContentDesigner.dll` (the Designs page and the studio) and its private assembly
`soft.square.net.ContentDesigner.Rendering.dll` (the canvas's renderers). The playground builds them for you:
`playground/out/contentdesigner.zip` and `playground/out/client/` (`Module.ContentDesigner.zip`).

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform               git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.ContentDesigner      this repo
```

(another location: `--property:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080,
client 5070), so stop the lab and any other playground first.

```bash
dotnet run --project playground --launch-profile dev
```

| Profile | What it does |
| --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.ContentDesigner.Web/bin/<Configuration>/net10.0` (`Modules:Local`), and the client parts from their build output (`ClientModules:Local`), Development only: installed and active on start. Change code, rebuild, restart the `webapi` resource in the dashboard |
| `install` | The platform starts without the module, as in production; upload `playground/out/contentdesigner.zip` on http://localhost:5070/host-modules (sign in as the dev platform admin) and activate it, then the API client's dll and `Module.ContentDesigner.zip` from `playground/out/client/` on http://localhost:5070/client-modules, in that order |

In Development the platform seeds the tenants `acme` and `globex`. The playground grants the module's permissions in
`acme` to the dev accounts through `Access:DevGrants`: `acme-admin@modular.local` gets `contentdesigner.*`,
`editor@modular.local` gets `contentdesigner.read`. Their passwords are in the platform's
`WebApi.Identity.Server/appsettings.Development.json`. Sign in on http://localhost:5070 as `acme-admin@modular.local`
and open **ContentDesigner** for the Designs page; the API is browsable at http://localhost:5080/scalar.

The designer works with other modules. In the `dev` profile, the playground loads each one that has a Debug build in a
checkout next to this repo, or at `--Playground:<Name>=<path>`, and grants the dev accounts its permissions:

| Module | Checkout | Used for |
| --- | --- | --- |
| DynamicFields | `../Module.DynamicFields` | Post kinds and block fields, validation, JSON-LD |
| Content | `../Module.Content` | Posts (documents) and their contents |
| Storage | `../Module.Storage` | Assets and the file picker (blobs in `playground/.data/blobs`) |
| Shifts | `../Module.Shifts` | Sections, including the department sections (Multimedia, SEO) |

A module without a build is skipped with a note at start. Elsa is not wired in yet.

Data stays in the Docker volume `contentdesigner-playground-data` and in `playground/.data`; delete both to start over.
